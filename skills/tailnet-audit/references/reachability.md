# 可达性矩阵怎么测、怎么读

## 为什么要分两层

| 层 | 命令 | 含义 |
| --- | --- | --- |
| 隧道层 | `tailscale ping <ip>` | 两台机器的 WireGuard 能不能对上话 |
| 端口层 | `nc -z -w3 <ip> <port>` | 上面的服务到底能不能连 |

只测一层会误判：

- 隧道通 + 端口全不通 → ACL 限了端口，或者服务只绑了局域网地址。
- 隧道不通 + 端口不通 → ACL 没给路由，或者设备离线。
- 隧道通 + 某端口通 → 真正要评估的暴露面。

## 矩阵怎么打

从「最危险的那台」出发，逐台逐端口测：

```bash
scripts/tailnet-recon.sh from --ssh root@203.0.113.10 --key ~/.ssh/deploy \
  --ports 22,445,139,5432,5433,6379,8090,8123,9091
```

输出是一张表：`来源 → 目标:端口 → 通/不通`。

## 怎么读

1. 先把「通」的格子全部列出来，每个格子问三句：这是什么服务、要不要认证、认证强度够不够。
2. 数据库、管理面板、SMB/NFS 这几类只要有一个格是「通」，就是 P0。
3. 「隧道通但全不通」要写进结论——它说明 ACL 起了作用，而不是运气好。
4. 结论里必须区分「实测」和「配置推断」：前者是跑出来的，后者是读 ACL 读出来的。

## 常见误判

- 目标机 `ss -tlnp` 显示 `0.0.0.0:5432`，但从外面连不上：可能是 UFW、云安全组、或 ACL 拦的。别直接下「安全」的结论，要说明是哪一层拦的。
- 用本机测觉得「全通」，换一台机器就「全不通」：说明 ACL 是按 tag/设备分的，这本身是好设计。
- 只测 TCP：UDP 服务（DNS、WireGuard、监控）要单独测，或者明确写「未测 UDP」。
